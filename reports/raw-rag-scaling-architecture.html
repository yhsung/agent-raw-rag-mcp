Raw-RAG 如何管理日漸膨脹的對話與向量索引？

基於 Litmeb/RAW-RAG (rag_adapter.py / rag_pgvector_store.py) 原始碼與本機實測數據：寫入端採用 Append-Only 增量尾部切塊（零表徵損失），讀取端採用 常數預算兩階段漏斗 + 時序重排展開（隔離 LLM Context 膨脹）。

寫入端單步計算複雜度
O(ΔL) · 0 LLM Calls
僅重切與嵌入最後一個未滿 256 tokens 的尾部區塊，歷史區塊完全鎖定不重算。
寫入期資訊流失 (Representation Loss)
0.0% (零有損壓縮)
對比複雜記憶系統在寫入期因 LLM 摘要/萃取直接損失 21.9% 狀態演進證據。
讀取端 Reader LLM 上下文上限
常數 O(k) ≈ 3.8K tokens
無論歷史膨脹至 32K、197K 或百萬 tokens，永遠只取 Top-128 → Rerank Top-15。

pgvector + 暫態釋放

1 架構對比：為什麼不在寫入端用 LLM 壓縮對話？

主流複雜記憶系統試圖在寫入時用 LLM 萃取「原子事實」或「摘要」來控制膨脹，實測卻造成永久表徵損失與碎片數量反向暴增 5.38 倍；Raw-RAG 則將「儲存增長」與「讀取視窗」徹底解耦。

2 寫入端機制：增量尾部切塊與嵌入 (Incremental Tail-Only Update)

當對話逐句增加時，RAGAdapter.add_incremental_message 不會重切或重算整段歷史。前 N-1 個已填滿 256 tokens 的區塊被標記為 stable_chunks（不可變），每次只重算最後一個未滿區塊與新延伸出的 tail_chunks。

對應實作：rag_adapter.py :: RAGAdapter.add_incremental_message (L335-L500) 增量日誌：rag_incremental_updates.jsonl

3 讀取與狀態演進管理：兩階段常數漏斗 + 時序重排 + 動態回合展開

既然資料庫不刪除舊狀態，當使用者反覆變更狀態（例如：台北 → 台南 → 取消改台中）時，Raw-RAG 如何避免舊資料誤導 Reader？關鍵在於「檢索時用 256-token 緊湊區塊，送給 LLM 前依原始時間排序並動態還原為完整對話回合」。

時序過濾：_filter_chunks_for_question_date (L1021-L1065) 時序重排：_selected_chunk_time_sort_key (L750-L766) 動態展開：_expand_chunk_to_turns (L1612-L1650)
